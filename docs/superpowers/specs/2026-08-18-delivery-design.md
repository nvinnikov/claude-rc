# claude-rc — доставка

Дата: 2026-08-18
Статус: дизайн утверждён, план не написан

Часть 3 из 3. Опирается на часть 1 (команда `claude-rc`) и часть 2 (`ClaudeRC.app`).

## Задача

После первых двух частей на машине есть тулза и приложение, но поставить их можно
только вручную: `uv tool install .` из клона плюс `make app` плюс перетаскивание
бандла. Обновление — те же три шага, которые надо помнить.

Нужны три канала, каждый под свой случай: себе на машину одной командой, чужому
человеку — ссылкой на релиз, и по-человечески — через Homebrew.

Отдельная проблема, всплывшая при работе над частью 1: на машине оказалось **два
клона** одного репозитория, и рабочий бот девятнадцать дней крутился не из того,
который правили. Устанавливаемая тулза этот класс путаницы убирает: код живёт в
одном месте, а не «в том клоне, откуда однажды запустили».

## Решения и их обоснование

| Решение | Выбор | Почему |
|---|---|---|
| Источник версии | `pyproject.toml` | Одно место. `Info.plist` и `claude-rc version` читают его же; расхождение версий тулзы и приложения — типовая причина «а у меня по-другому». |
| Тег и релиз | `v<версия>`, релиз собирается по тегу | Тег — единственный триггер. Ручная сборка релиза руками рано или поздно даст артефакт, не соответствующий коду. |
| Подпись приложения | Ad-hoc | Developer ID стоит денег и требует аккаунта. Проверено в части 2: `SMAppService` ad-hoc принимает, автозапуск работает. Цена — карантин при первом запуске скачанного бандла, снимается одной командой из README. |
| Формат артефакта | `.zip` бандла | `.dmg` требует лишних шагов сборки и ничего не даёт: приложение ставится перетаскиванием либо через cask. |
| Homebrew | Формула для CLI + cask для приложения, cask зависит от формулы | Единственный способ поставить обе части одной командой. Разделение обязательно: формулы ставят бинари, каски — бандлы. |
| Репозиторий tap | Отдельный `nvinnikov/homebrew-tap`, создаёт человек | У меня нет доступа заводить репозитории. Файлы формулы и cask пишем здесь, инструкцию — в README. |
| Проверка Swift в CI | Отдельная job на macOS-раннере | Python-часть гоняется на ubuntu и про Swift ничего не знает. Без этой job приложение ломалось бы незаметно. |

## Архитектура

```
   pyproject.toml (version)
        │
        ├──▶ claude-rc version        (importlib.metadata)
        ├──▶ Info.plist               (make-app.sh)
        └──▶ тег v<версия>            (проверяется в CI)
                    │
                    ▼
        .github/workflows/release.yml
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
   ClaudeRC.app.zip         sdist + wheel
        │                        │
        └────────┬───────────────┘
                 ▼
          GitHub Release
                 │
                 ▼
      nvinnikov/homebrew-tap
        formula claude-rc  ──▶ CLI
        cask claude-rc-app ──▶ .app (depends_on formula)
```

### `make install`

Одна цель, делающая всё, что человек иначе делает руками:

```
make install-tool   # uv tool install --force .
make install-app    # make app + перенос в /Applications
make install        # обе
```

Разделение не косметическое: тулза нужна и без приложения (например, на машине
без графики), а приложение без тулзы бессмысленно — `install-app` зависит от
`install-tool`.

Перенос в `/Applications` перезаписывает существующий бандл. Если приложение
запущено, его надо сначала погасить — цель делает это сама и говорит об этом,
иначе `cp` положит файлы под работающим процессом.

### Релизный workflow

`.github/workflows/release.yml`, триггер — тег `v*`.

1. **Проверка версии.** Тег `v0.2.0` обязан совпасть с `version` в `pyproject.toml`.
   Не совпал — job падает до всякой сборки. Это единственная защита от релиза,
   в котором `claude-rc version` печатает не то, что написано на странице релиза.
2. **Гейт.** `make check` на ubuntu — тот же, что в CI.
3. **Сборка приложения** на `macos-latest`: `make app`, затем zip бандла с
   сохранением прав и симлинков (`ditto -c -k --keepParent`, а не `zip`: обычный
   `zip` теряет атрибуты бандла и подпись перестаёт проверяться).
4. **Сборка пакета**: `uv build` → sdist и wheel.
5. **Публикация**: оба артефакта прикрепляются к релизу, тело релиза берётся из
   `CHANGELOG.md`, если он есть, иначе — из сообщений коммитов с прошлого тега.

Раннер macOS в GitHub Actions идёт с полным Xcode, так что сборка там строго
проще, чем локально: наш скрипт не зависит от Xcode вовсе.

### Homebrew tap

Два файла в `packaging/homebrew/`, откуда человек копирует их в свой tap:

- `claude-rc.rb` — формула. Ставит CLI из sdist релиза через `virtualenv_install_with_resources`,
  объявляет зависимость от `python@3.12` и от `tmux`.
- `claude-rc-app.rb` — cask. Ставит `ClaudeRC.app` из zip релиза, объявляет
  `depends_on formula: "claude-rc"`.

Оба содержат `sha256`, который меняется с каждым релизом. Обновлять их вручную —
работа, поэтому релизный workflow дополнительно печатает готовые строки с
подсчитанными хешами: скопировать в tap проще, чем считать.

Автоматический пуш в tap не делаем: это второй репозиторий, и токен с правом
записи в него пришлось бы держать в секретах этого. Размен не в нашу пользу.

### Проверка Swift в CI

В `ci.yml` добавляется job `app` на `macos-latest`: `swift test --package-path app`
и `make app`. Без неё Swift-часть не проверяется вообще — весь остальной CI живёт
на ubuntu.

## Ошибки

| Ситуация | Поведение |
|---|---|
| Тег не совпал с версией в `pyproject.toml` | Релиз падает до сборки, с внятным сообщением |
| `/Applications` недоступен | `make install-app` падает, тулза при этом уже установлена |
| Приложение запущено при установке | Цель гасит его и сообщает об этом |
| Скачанный бандл в карантине | README называет команду снятия — это последствие ad-hoc подписи, а не поломка |
| Homebrew tap не создан | Формула и cask лежат в репозитории, README объясняет, что с ними делать |

## Тестирование

Автотестов у доставки нет: предмет — сборка и публикация, а их проверка требует
настоящего тега и настоящего релиза. Вместо этого:

- проверка версии в workflow — сама себе тест, и она обязана падать на расхождении;
- `make install` проверяется прогоном на этой машине с последующим `claude-rc doctor`
  из чужого каталога;
- релизный workflow проверяется одним настоящим тегом `v0.2.0` и осмотром артефактов.

## Вне объёма

- Нотаризация и Developer ID. Требуют платного аккаунта; ad-hoc проверен и работает,
  цена — одна команда снятия карантина при первом запуске.
- Автоматический пуш в homebrew-tap.
- Публикация в PyPI. Тулза однопользовательская и завязана на локальный `claude`;
  в индексе ей делать нечего.
- Автообновление приложения.

## Границы

Раздел «Границы» из CLAUDE.md не двигается. Доставка ничего не меняет в модели прав:
кто прошёл `allowed_user_id`, получает на машине полноценный Claude Code. Установка
через Homebrew этого не усиливает и не ослабляет.
