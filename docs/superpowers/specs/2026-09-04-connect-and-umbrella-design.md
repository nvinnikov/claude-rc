# claude-rc вместо суперсета: connect, --host и зонтичные каталоги

Дата: 2026-09-04

## Зачем

Разработка идёт на домашнем сервере, а управляется с телефона и со второго компьютера.
Требование к такой схеме одно: закрытый ноутбук не должен ничего останавливать. Ровно
это `claude-rc` уже делает — сессия принадлежит tmux, а не тому, кто её запустил.

[Superset](https://superset.sh/) продаёт ту же функцию (remote-режим, Pro-подписка):
поднимает туннель между машиной и SSH-сервером и показывает сессии в своём окне. Оттуда
и ощущение «отнимает контроль» — весь вход в систему идёт через чужой UI, а не через
терминал и не через уже имеющиеся инструменты.

Сверка того, что нужно, с тем, что есть:

| Что нужно | Сейчас |
|---|---|
| Сессии живут на сервере и переживают закрытие ноутбука | есть: tmux-сессии `rc-<имя>` |
| Управление с телефона | есть: Telegram-бот отдаёт ссылку, дальше приложение Claude |
| Подсесть к сессии **из терминала другого компьютера** | нет: `attach_command` — подсказка только для самой машины |
| Поднять сессию, не заходя на сервер руками | нет: CLI работает только там, где запущен |
| Сессия над **зонтиком из репозиториев** (`/services/*`) | почти есть: запуск работает, но зонтик не виден в списке проектов, а `sync` по явному пути его отвергает |

Три последние строки и есть предмет этого документа.

## Что выяснилось про Claude Code

Прежде чем проектировать своё, стоит знать, что уже умеет сам `claude` — часть работы
делать не надо, а часть надо делать иначе.

1. **`claude --add-dir A B`** — несколько рабочих каталогов в одной сессии. Выглядит как
   ответ на «объединённые репозитории», но документация оговаривает: `.claude/` (настройки,
   хуки, `CLAUDE.md`) **не подхватывается** из добавленных каталогов, только из основного
   `cwd`. Для раскладки `/services/*` зонтичный каталог поэтому лучше (блок 3): там всё
   внутри рабочего дерева и вложенные конфигурации работают как обычно.

2. **`claude remote-control` — серверный режим.** Один процесс, до 32 сессий, создаются
   по требованию из claude.ai и приложения; `--spawn worktree` заводит на каждую свой
   worktree. Это половина функциональности бота, но в пределах одного каталога-корня и
   без отдельной панели tmux на сессию — значит, без подсадки из терминала.
   Не замена нашей модели, но полезное дополнение (блок 4).

3. **`claude --bg` / `claude attach <id>` / `claude agents`** — своя подсистема фоновых
   сессий с супервизором. Механизм отдельный от Remote Control; переезжать на него
   незачем: интерактивная RC-сессия всё равно требует tty, а tmux даёт и tty, и подсадку.

4. Документация Remote Control прямым текстом рекомендует то, что уже сделано:
   *«To keep a session running on a remote machine after you disconnect from SSH, start it
   inside tmux or screen»*. Текущая конструкция — не обход, а автоматизация штатного пути.

## Три поверхности одной сессии

Смысл Remote Control — начать сессию на сервере и дальше работать в ней с чего угодно.
Поверхностей у неё ровно три, и путать их не надо.

**Приложение Claude и браузер — уже работает, писать нечего.** RC-сессия зарегистрирована
в API, и её клиенты по документации — claude.ai, мобильные приложения **и Claude Desktop**
(раздел Trusted Devices: *«view or steer Remote Control sessions from claude.ai, the Claude
mobile apps, or Claude Desktop»*). На втором компьютере приложение Claude показывает тот же
список сессий, что телефон. Это и есть «подключиться с компа как с телефона», и никакой
код для этого не нужен.

**Терминал — только через tmux.** Клиентского режима «стань терминалом для вон той
RC-сессии» в CLI нет, и подделать его нечем:

* `claude --resume <id>` во втором терминале не подключается к живой сессии, а поднимает
  новый локальный процесс поверх того же транскрипта. Документация: *«If you resume the
  conversation in a second terminal while the first one still has Remote Control on, Claude
  Code prints a notice in the second terminal and leaves Remote Control off there instead of
  taking the session away from the first»*, а если запустить две — *«messages from both
  interleave into one transcript»*. Плюс транскрипт лежит на сервере, а не на ноутбуке.
* `--teleport` поднимает в локальном терминале сессию Claude Code **on the web**, то есть
  облачную, а не RC-сессию с другой машины.

Значит, попасть терминалом внутрь живой RC-сессии можно единственным способом — прийти
в тот терминал, где она живёт. Он в панели tmux на сервере. Блок 1 открывает эту дверь,
и это не «хоть так», а единственный путь.

**Telegram — управление, а не работа.** Поднять, погасить, посмотреть список; разговор
идёт в двух поверхностях выше.

Отсюда приоритет: блок 1 закрывает единственную по-настоящему отсутствующую поверхность.
Блок 2 (`--host`) не про подключение вовсе — он про удобство управления, и потому идёт
последним.

## Блок 1. `claude-rc connect`

Подсадка к живой сессии как к обычному терминалу. Работает и на самой машине, и через
SSH со второго компьютера.

### Контракт

```
claude-rc connect [target] [--start] [--branch B] [--read-only] [--url]
```

| Аргумент | Смысл |
|---|---|
| `target` | имя сессии, каталог или пусто |
| `--start` | нет сессии — поднять и сразу подсесть |
| `--branch` | только вместе с `--start`: worktree под ветку, как у `start` |
| `--read-only` | `tmux attach -r`: смотреть, не вводя |
| `--url` | напечатать ссылку и выйти, ничего не открывая |

Разрешение цели — в том же порядке, что у остальных команд:

1. пусто и живая сессия одна — она;
2. пусто и сессий несколько — при tty нумерованный выбор, без tty список и код 2;
3. цель похожа на путь (существует как каталог или содержит `/`) — `remote.find(realpath)`;
4. иначе имя — `remote.get_session(name)`, при промахе частичное совпадение по имени
   (одно совпадение — берём, несколько — печатаем список и код 2).

Коды возврата — те же, что в CLI сейчас: 1 «попробовали, не вышло», 2 «не с чем работать».
При успехе `connect` не возвращается: процесс замещается tmux.

### Реализация

В `remote.py` появляется единственный источник правды по аргументам подсадки:

```python
def attach_argv(tmux_name: str, *, read_only: bool = False, detach_others: bool = False) -> list[str]:
    """Полный argv для подсадки, включая `-L` при своём сокете."""
```

`attach_command` перестаёт склеивать строку руками и становится
`shlex.join(attach_argv(...))` — подсказка в боте и реальный запуск не смогут разойтись.
Цель — `=<имя>`: `attach-session` принимает target-session, где `=` значит точное
совпадение (двоеточие тут не нужно, оно требуется только там, где ждут target-pane).

Сам запуск — `os.execvp("tmux", argv)` после того, как `asyncio.run` вернул сессию.
`exec`, а не `subprocess`: tty должен достаться tmux напрямую, а нам после этого нечего
делать.

### Грабли

- **`-d` при подсадке обязателен.** Панель создаётся `-x 120 -y 40` без клиента. Второй
  клиент меньшего размера ужмёт окно обоим — TUI переверстается прямо под руками у того,
  кто работает. `attach -d` отключает прочих клиентов; это и есть ожидаемое поведение для
  «перенести сессию сюда». Для подсказки в боте `detach_others` остаётся `False`: там
  человек читает команду глазами и не ждёт, что она кого-то отцепит.
- **Ссылку переподключение не теряет** — она в `@rc_url`, а не в буфере панели. Это ровно
  та причина, по которой её туда клали; тест на connect должен это зафиксировать, иначе
  при следующем рефакторинге инвариант потеряется молча.
- **Без tty подсаживаться нельзя.** `claude-rc connect` из скрипта или из `ssh` без `-t`
  даст `open terminal failed`. Проверяем `sys.stdin.isatty()` заранее и отвечаем кодом 2
  с подсказкой про `ssh -t`, а не пробрасываем ошибку tmux.
- **Watcher и выход из сессии.** Если подсевший человек выйдет из claude (`/exit`), панель
  завершится, tmux-сессия исчезнет, и watcher отчитается в Telegram «сессия упала» —
  формально он прав, но человек-то вышел сам. Гасить сессию мимо watcher нельзя (записано
  в граблях), поэтому вариантов два: либо `connect` метит сессию как «есть подсевший
  клиент» и watcher смягчает формулировку, либо формулировка watcher'а становится
  нейтральной («сессия завершилась»). Второе дешевле и честнее.

### Тесты

- `attach_argv` даёт `=имя` и подставляет `-L` при `CLAUDE_RC_TMUX_SOCKET` (расширение
  существующих тестов `attach_command`);
- `-d` есть при подсадке и нет в подсказке;
- разрешение цели: по каталогу через `realpath` (два клона одного репо не путаются),
  по имени, по частичному совпадению, неоднозначность даёт код 2;
- нет сессии и нет `--start` — код 1 с внятным текстом;
- `--start` зовёт `launch` и только потом `exec` (подменяем `os.execvp`);
- не tty — код 2 и подсказка про `ssh -t`, `execvp` не вызывался.

## Блок 2. Флаг `--host`: тот же CLI, но выполняется на сервере

Это **не** способ подключиться к сессии — подключение закрыто блоком 1 и приложением
Claude. Это способ завести сессию, посмотреть список и синхронизировать репозитории,
не заходя на сервер руками. Удобство, а не суть, поэтому делается последним.

```bash
claude-rc --host home sessions
claude-rc --host home start ~/code/api --branch feat/x
claude-rc --host home connect api
```

Транспорт — обычный SSH. Своего демона, своего протокола и своего порта не заводим:
аутентификация, шифрование и ключи у SSH уже есть, а любая наша замена была бы хуже.

### Реализация

Новый модуль `clauderc/proxy.py`:

```python
def remote_argv(host: str, args: list[str], *, tty: bool) -> list[str]:
    """ssh [-t|-T] host claude-rc <args>, каждый аргумент через shlex.quote."""
```

`cli.run()` перед разбором подкоманд решает, локальный это запуск или проксируемый, и во
втором случае замещает процесс через `os.execvp("ssh", ...)`. Замещение опять же удобно:
коды возврата, stdout/stderr и Ctrl+C достаются SSH без нашего посредничества.

`tty=True` нужен командам, где человек отвечает на вопрос: `connect`, `setup`, `start`
(диалог доверия каталогу). Остальным — `-T`.

Хост берётся из `--host`, иначе `CLAUDE_RC_HOST`, иначе `[remote] host` в конфиге.

### Грабли

- **`load_config` на клиенте не годится.** Она требует `bot_token` и `allowed_user_id`
  (`KeyError` при отсутствии) и проверяет существование `rc_roots`. На ноутбуке ни токена,
  ни этих каталогов нет и быть не должно — токен живёт только на сервере. Нужен отдельный
  маленький ридер `[remote]`, читающий тот же файл, но не требующий ничего из бота.
  Тащить боевой токен на ноутбук ради флага `--host` — прямо противоположное тому, ради
  чего конфиг не попадает в git.
- **Относительные пути ядовиты.** `claude-rc --host home start .` подставит каталог
  ноутбука. Либо на клиенте запрещаем относительные пути (`start .` без `--host` работает
  как раньше), либо разворачиваем их на сервере — но молча резолвить локально нельзя.
- **Каждый аргумент через `shlex.quote`.** Аргументы уходят в удалённый shell; это пункт 2
  чеклиста ревью, и здесь он не теоретический.
- **`--host` не должен проксировать `bot`.** Запустить бота на сервере через SSH-сессию,
  которая умрёт вместе с терминалом, — не то, чего человек хочет. Команда `bot` при
  `--host` отклоняется с объяснением.
- Для мобильного канала (тетеринг, поезд) `mosh` переживает разрывы куда лучше `ssh`.
  Просится `[remote] transport = "ssh" | "mosh"`, но это уже после того, как заработает
  базовый вариант.

### Тесты

- `remote_argv` квотит аргументы с пробелами и кавычками;
- `-t` для `connect`/`setup`/`start`, `-T` для остальных;
- приоритет `--host` > `CLAUDE_RC_HOST` > конфиг;
- ридер `[remote]` не падает на конфиге без `bot_token` и без существующих `rc_roots`;
- `--host` + `bot` — код 2, `execvp` не вызывался;
- относительный путь при `--host` — код 2.

## Блок 3. Зонтичные каталоги

Типовая раскладка — не «репозитории, разбросанные по дереву», а зонтик без своего `.git`:

```
/services            ← сессия поднимается здесь
/services/repo-1
/services/repo-n
```

Claude, запущенный из `/services`, видит все сервисы разом, и вложенные `CLAUDE.md`
и настройки каждого репозитория работают обычным образом — они внутри рабочего дерева.
Это строго лучше, чем `--add-dir`: добавленные каталоги, по документации, не отдают
`.claude/` вовсе. Поэтому основной механизм для «объединённых репозиториев» —
зонтик, а не группы.

### Что уже работает

- `claude-rc start /services` — `start` проверяет только `is_dir()`, git не требуется;
- кнопка «▶️ Start Claude RC» в карточке навигации есть у любого каталога, не только
  у репозитория (`--branch` предлагается лишь в git-каталоге, и это верно);
- `worktrees.ensure` в не-git каталоге отвечает внятно, а не сырой ошибкой git;
- кнопка «🔄 Sync» в зонтике работает: `sync.list_repos` берёт прямых детей;
- история и `--resume` для `/services` работают — слаг каталога от наличия git не зависит.

То есть сценарий уже поддержан. Дыр ровно две.

### Дыра 1: зонтик не попадает в список проектов

`repos.discover` отдаёт сами корни плюс всё, у чего есть `.git`. Зонтик своего `.git`
не имеет, поэтому `/services` в списке не появляется — видны только его дети. Дойти до
него можно лишь через `/cd` или сделав его отдельным корнем в `rc_roots`.

Чинится в `_walk`: каталог без `.git`, у которого есть git-дети, — тоже валидная цель.
Порог — **не меньше двух** git-детей: при одном зонтик почти дублирует сам репозиторий
и только зашумляет список. Стоимость нулевая, `.git` детей всё равно проверяется на этом
же проходе.

В карточке проектов зонтик надо отличать от репозитория (в навигации репозитории уже
метятся `●`), иначе непонятно, почему у одной кнопки есть «New worktree», а у другой нет.

### Дыра 2: `sync <зонтик>` с явным путём отказывает

```python
resolve_targets([Path("/services")])  # → [] : is_repo() False, путь отброшен
```

При этом `cd /services && claude-rc sync` работает — там `list_repos(cwd)` разворачивает
каталог в детей. Бот и CLI расходятся на одном и том же дереве.

Само по себе это мелочь, но с блоком 2 она становится заметной: через `--host` путь
**всегда** явный, и `claude-rc --host home sync /services` — ровно тот вызов, который
хочется сделать, и ровно тот, который сейчас ответит «не git-репозиторий, пропущен».

Чинится в `resolve_targets`: явный путь, который не репозиторий, но содержит
репозитории, разворачивается через `list_repos` — тем же способом, что и текущий
каталог. Явный путь, где репозиториев нет вовсе, по-прежнему попадает в
`rejected_paths` и называется человеку.

### Что остаётся от групп

`--add-dir` нужен только там, где репозитории лежат под разными родителями
(`~/code/api` и `~/work/shared`) и зонтик над ними не построить. Это не текущий сценарий,
и секцию `[[groups]]` в конфиге заводить рано: сначала зонтики, а группы — если
раскладка когда-нибудь окажется именно такой. Если делать, помнить две вещи: ключ сессии
остаётся каталогом (значит, у группы обязателен единственный главный каталог, и две
группы с одним главным конфиг должен отклонять), а `.claude/` из добавленных каталогов
не читается.

### Тесты

- `discover` отдаёт каталог без `.git` с двумя git-детьми и не отдаёт с одним;
- зонтик не дублируется, если он же указан в `rc_roots`;
- `resolve_targets([зонтик])` даёт его репозитории;
- `resolve_targets([пустой каталог])` даёт пусто, и путь называется в `rejected_paths`;
- `resolve_targets([репозиторий])` не изменился;
- `start` в каталоге без `.git` поднимает сессию; `start --branch` там же отвечает
  «не git-репозиторий, worktree делать негде».

## Блок 4 (опционально). `claude-rc serve <каталог>`

Обёртка над `claude remote-control --spawn worktree` в tmux-панели: один процесс, а сессии
внутри него человек плодит прямо из приложения Claude, без Telegram и без ручного
worktree. Это лучший ответ на «хочу быстро начать новую сессию», когда речь про один
большой репозиторий.

Ограничения, из-за которых это дополнение, а не замена: сервер привязан к одному
каталогу-корню, к его сессиям нельзя подсесть отдельной панелью, и они не видны в
`remote.list_sessions` как обычные `rc-*`. Делать после первых трёх блоков и только если
режим окажется удобным на практике.

## Чего не делаем

- **Своего демона и своего протокола.** SSH уже решает эту задачу, и любая наша замена
  добавила бы поверхность атаки к машине, где, как записано в «Границах», лежат все токены.
- **Переезда с tmux на `claude --bg`.** Другой механизм, без tty-панели, а значит без
  подсадки из терминала — то есть без главного, ради чего всё затевается.
- **Автоподтверждения диалога доверия при `--host`.** Через SSH соблазн особенно велик, но
  это решение о правах на каталог, и оно остаётся за человеком. `-t` даёт возможность
  ответить; больше ничего не нужно.
- **Гейта прав в боте или в CLI.** Границы не двигаются: кто прошёл `allowed_user_id`,
  получает полноценный Claude Code на машине. `--host` ничего здесь не меняет — он лишь
  ещё один способ дотянуться до того же CLI поверх SSH, где своя аутентификация.

## План работ

Каждый этап — свой коммит, `make check` зелёный перед каждым.

0. **Проверить приложение Claude на втором компьютере** — возможно, «как с телефона»
   закрывается без кода, и остаётся только терминал.
1. **`attach_argv` в `remote.py`** плюс перевод `attach_command` на него. Поведение
   подсказки не меняется, тесты обновляются на `=имя`.
2. **`claude-rc connect`**: разрешение цели, проверка tty, `execvp`, `--read-only`,
   `--url`. Без `--start`.
3. **`connect --start [--branch]`**: переиспользует `_start` и `_ask_trust` из CLI.
4. **Формулировка watcher'а** при исчезновении сессии — нейтральная, чтобы выход из
   подсаженной сессии не выглядел падением.
5. **Зонтики**: `discover` отдаёт каталог с двумя и более git-детьми, `resolve_targets`
   разворачивает явный не-git путь через `list_repos`, зонтик помечен в карточке проектов.
6. **`clauderc/proxy.py` и флаг `--host`** плюс отдельный ридер `[remote]`.
7. **Документация**: `README.md` и `README.ru.md` синхронно, новые грабли — в `CLAUDE.md`
   и в раздел «Design notes» английского README.

Этапы 1–4 закрывают единственную отсутствующую поверхность — терминал на втором
компьютере. Этап 5 дешевле остальных: сценарий с зонтиком уже поддержан, закрываются
две дыры вокруг него. Этап 6 — удобство поверх готового.

## Что править в документации

- `README.md` / `README.ru.md`: раздел про подсадку («you can attach from the machine
  itself») перестаёт быть про «с машины» и становится про «с любой машины»; новые команды
  `connect`, флаг `--host`, секция `[remote]` в `config.example.toml`, зонтичные каталоги
  как штатный способ работать с `/services/*`.
- `CLAUDE.md`: в «Грабли» — `-d` при подсадке, конфиг клиента без токена, расхождение
  `resolve_targets` и `list_repos` на явном пути, `.claude/` не берётся из `--add-dir`.
  В «Структуру» — `proxy.py`.
